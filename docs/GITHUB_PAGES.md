# Как опубликовать «Бакнин» на GitHub Pages

Основной результат проекта — сайт, который посетитель открывает по HTTPS-ссылке.
В обычном процессе публикации все действия выполняются в браузере на GitHub.
Устанавливать Python, Node.js, зависимости или запускать локальный сервер не требуется.

Сайт собирает процесс [`.github/workflows/pages.yml`](../.github/workflows/pages.yml)
с названием **Publish GitHub Pages**. Он использует Node.js и публикует готовые
HTML, CSS, JavaScript и публичные данные. Flask и SQLite на Pages не запускаются.
Русский анализ работает словарными правилами в браузере; Python-модель туда не переносится.

## Перед публикацией

Нужен доступ к настройкам репозитория
[Sweaty6/Baknin_Project](https://github.com/Sweaty6/Baknin_Project).
Для публичных репозиториев Pages доступен на GitHub Free. Для частного репозитория
нужен тариф с поддержкой Pages, например GitHub Pro или подходящий тариф организации.
Если рассматриваете изменение видимости на public, учитывайте: исходники и все
отслеживаемые файлы репозитория станут общедоступными. Публиковать закрытый корпус,
локальную базу или секреты для этого не нужно. Сам сайт Pages обычно публичный.

В репозитории должна быть ветка `main` с исходниками проекта. На вкладке **Code**
проверьте наличие файлов и папок:

```text
.github/workflows/pages.yml
scripts/build_website.mjs
website/
website/data/catalog.json
website/data/reviews.json
```

Если они уже есть, перейдите сразу к следующему разделу. Для загрузки проекта
в другой репозиторий через браузер:

1. Создайте пустой репозиторий на GitHub и распакуйте архив проекта у себя.
2. Откройте **Code → Add file → Upload files**. В новом пустом репозитории
   ссылка может называться **uploading an existing file**.
3. Загрузите содержимое папки проекта, сохраняя структуру каталогов.
   Не загружайте весь проект одной дополнительной папкой `Baknin_Project-main`.
   Не добавляйте `.git`, `.venv`, `venv`, `instance` и крупные старые архивы.
4. Убедитесь, что `.github/workflows/pages.yml` попал в репозиторий:
   папки с точкой могут быть скрыты в Проводнике.
5. Внизу страницы напишите описание, например «Добавлен сайт»,
   и нажмите **Commit changes** в ветку `main`.

Процесс GitHub Pages запускает только доверенный код из вашего проекта.
Загрузка одного ZIP как файла не распаковывает его на GitHub и не создаёт сайт.

## 1. Разрешить GitHub Actions

Откройте [вкладку Actions](https://github.com/Sweaty6/Baknin_Project/actions).
Если GitHub показывает кнопку включения процессов, нажмите
**I understand my workflows, go ahead and enable them**.

Если процессы запрещены настройками репозитория, откройте
**Settings → Actions → General** и разрешите используемые GitHub Actions,
если у вас есть нужные права. Политики организации может изменять её администратор.
Сам файл публикации уже запрашивает необходимые разрешения `pages: write`
и `id-token: write`; отдельный токен в Secrets для обычной публикации не нужен.

## 2. Включить GitHub Pages

1. Откройте репозиторий и нажмите **Settings** в верхнем меню.
2. В левом меню выберите **Pages** в разделе **Code and automation**.
   Прямая ссылка: [Settings → Pages](https://github.com/Sweaty6/Baknin_Project/settings/pages).
3. Найдите **Build and deployment**.
4. В поле **Source** выберите **GitHub Actions**.

Это основной режим. Не выбирайте здесь корень `main`: в нём исходники,
а готовый сайт создаётся отдельной сборкой. Настройки домена и HTTPS для
стандартного адреса `github.io` менять не требуется.

### Если ранее публиковали с ветки `gh-pages`

GitHub может оставить правило, разрешающее публикацию только из `gh-pages`.
При новом workflow публикация выполняется из `main`:

1. Откройте **Settings → Environments**.
2. Выберите окружение **github-pages**.
3. Найдите **Deployment branches and tags**.
4. При режиме **Selected branches and tags** нажмите **Add deployment branch or tag rule**.
5. Выберите **Branch** и укажите точное имя **main**, затем сохраните.

Существующее правило `gh-pages` можно сохранить. Не требуется разрешать все ветки.
Без правила для `main` GitHub может отклонить Deploy website с сообщением
`Branch "main" is not allowed to deploy to github-pages due to environment protection rules`.
Это проверка настроек размещения, а не ошибка HTML или анализа текста.

## 3. Запустить публикацию

1. Перейдите во вкладку **Actions**.
2. В списке процессов слева выберите **Publish GitHub Pages**.
3. Справа нажмите **Run workflow**.
4. В поле ветки выберите **main** и нажмите зелёную кнопку **Run workflow**.
5. Обновите страницу. Откройте появившийся запуск и дождитесь завершения.

Публикация обычно занимает несколько минут. Зелёная отметка означает успешный
запуск; жёлтая — работа продолжается; красная — возникла ошибка. Откройте
красный шаг и прочитайте его сообщение, прежде чем повторять запуск.

Если после включения Pages вы уже сохранили изменение в `main`, процесс может
запуститься автоматически. Дополнительный ручной запуск тогда не обязателен.

## 4. Открыть и проверить сайт

В **Settings → Pages** после успешной публикации появится адрес сайта
и кнопка **Visit site**. Ссылка также видна в результате задания публикации.
Для этого репозитория ожидаемый адрес:

**https://sweaty6.github.io/Baknin_Project/**

Часть `/Baknin_Project/` обязательна; соблюдайте регистр букв имени репозитория.
Если используете свой аккаунт или другое имя репозитория, адрес изменится на
`https://ИМЯ-АККАУНТА.github.io/ИМЯ-РЕПОЗИТОРИЯ/`.

Проверьте каталог, переход в карточку вуза, раздел отзывов, анализ и методику.
В анализе введите русский текст и отправьте его. Проверьте также сайт на телефоне.
Отсутствие отзывов и сообщение «Недостаточно данных» сейчас ожидаемы:
в комплекте есть справочник вузов, но нет настоящего корпуса.

## Обновить страницы сайта

1. Откройте нужный файл на вкладке **Code**: страницы находятся в `templates/`,
   оформление — в `static/style.css`, браузерное поведение — в `static/app.js`.
2. Нажмите значок карандаша **Edit this file**.
3. Сохраните изменения кнопкой **Commit changes** в `main`.
4. Откройте **Actions** и дождитесь зелёного результата новой публикации.
5. Обновите страницу сайта. Если браузер показывает старую версию,
   используйте Ctrl+F5 или откройте ссылку в приватном окне.

Сохранение исходников в режиме GitHub Actions автоматически запускает новую
публикацию. Пользователю сайта не нужно скачивать новую версию или перезапускать сервер.

## Обновить каталог и отзывы

Канонические публичные данные сайта хранятся в:

- [`website/data/catalog.json`](../website/data/catalog.json) — справочник вузов;
- [`website/data/reviews.json`](../website/data/reviews.json) — проверенные публичные отзывы.

Для изменения каталога откройте `catalog.json` через GitHub, нажмите карандаш
и измените соответствующую запись внутри `universities`, сохранив её `id`.
В том же файле есть `schema_version` и настройки `settings`: не удаляйте их.
Используйте официальные названия, города, регионы и HTTPS-адреса. Сохраняйте
правильный JSON: двойные кавычки, запятые между объектами, без запятой после
последнего объекта.

`reviews.json` в комплекте — пустой массив `[]`. Полный формат записей описан в
[website/data/README.md](../website/data/README.md). Добавляйте только реальные
отзывы, принадлежащие указанному вузу, с источником и подтверждённой ручной разметкой.
Требуются даты, источник, идентификатор вуза, тональность и флаги проверки;
сам результат словарных правил не делает запись пригодной для рейтинга.

Проверьте допустимость публичного показа и удалите ненужные персональные данные
до загрузки файла. Все сведения в `website/data`, включая метаданные, предназначены
для публикации; закрытый корпус и локальную SQLite сюда не копируют.
При `display_allowed: false` исходный текст и цитаты тем должны уже быть `null`
до загрузки в GitHub. Флаг не скрывает информацию, которая попала в историю Git.

Не заполняйте рейтинг вымышленными отзывами. Текст, введённый посетителем
на странице анализа, автоматически отзывом не становится. Результаты словарных
правил также не заменяют ручную проверку данных для рейтинга.

После изменения данных нажмите **Commit changes** в `main` и дождитесь
успешной сборки в Actions. Сборка проверяет структуру данных; если она отклоняет
запись, прочитайте ошибку и исправьте исходный JSON. Пустой массив отзывов `[]`
допустим и означает отсутствие опубликованного корпуса.

## Если что-то не работает

| Ситуация | Что проверить |
|---|---|
| Нет **Settings** или нельзя менять **Pages** | Нужны права управления репозиторием; откройте свой репозиторий или обратитесь к его владельцу. |
| Pages недоступен для private-репозитория | Проверьте поддержку Pages вашим тарифом. Изменение на public открывает исходники; не меняйте видимость только ради устранения ошибки без оценки публикуемых файлов. |
| Нет **Publish GitHub Pages** или **Run workflow** | Проверьте наличие `.github/workflows/pages.yml` в `main`, включение Actions и поле `workflow_dispatch` в файле процесса. |
| Ошибка **Configure Pages**, `Get Pages site failed` или 404 при конфигурации | Сначала включите **Settings → Pages → Source: GitHub Actions**. Проверьте поддержку Pages и права, затем повторите запуск. |
| Ошибка проверки данных или сборки | Откройте красный шаг **Build public website** и исправьте указанный файл в `website/data` или исходники. |
| Ошибка разрешений публикации | Убедитесь, что запущен штатный процесс из `main` и его разрешения не запрещены политиками организации. Не добавляйте случайные токены. |
| `Branch "main" is not allowed to deploy to github-pages` | Settings → Environments → github-pages → Deployment branches and tags: добавьте разрешённую ветку `main`, затем повторите Run workflow. |
| Весь сайт отвечает 404 | Проверьте полный адрес с `/Baknin_Project/`, включение Pages и зелёный результат публикации. После первого запуска дайте Pages несколько минут. |
| Главная открывается, но нет оформления или внутренних страниц | Проверьте путь репозитория в ссылках и сборке. Для этого проекта базовый путь — `/Baknin_Project/`, а не `/`. |
| Новые изменения не видны | Убедитесь, что изменена ветка `main`, последняя публикация успешна и выбран Source GitHub Actions. Обновите страницу с очисткой кеша. |
| «Недостаточно данных» | Сайт работает; для рейтинга пока нет нужной подтверждённой выборки. |

## Резервный способ: готовая ветка `gh-pages`

Этот вариант подходит, если в репозитории уже есть подготовленная ветка `gh-pages`
с готовыми HTML, CSS, JavaScript и данными. Она должна содержать `index.html`
в своём корне. Исходники в `main` и архив ZIP не заменяют такой готовый сайт.

1. Откройте **Settings → Pages → Build and deployment**.
2. Выберите **Source: Deploy from a branch**.
3. В поле **Branch** выберите **gh-pages**, рядом — **/ (root)**.
4. Нажмите **Save** и дождитесь публикации.

В этом режиме Pages публикует содержимое `gh-pages`. Изменения только в `main`
не обновляют снимок в этой ветке автоматически. Для следующих релизов нужно
заново собрать и обновить `gh-pages` либо вернуться к основному режиму GitHub Actions.
Два режима публикации имеют разные источники; для автоматических обновлений
используйте Source GitHub Actions.

## Необязательно: собрать и проверить сайт на компьютере

Этот раздел нужен разработчику; для размещения через GitHub он не требуется.
Установите Node.js 20 или новее, предпочтительно актуальную LTS-версию,
распакуйте проект и откройте терминал в папке с `package.json`, `scripts`
и `website`. Затем:

```bash
npm ci
npm run build -- --base-path /Baknin_Project/
npm run preview
```

`npm ci` один раз устанавливает зафиксированные Node-зависимости.
Повторяйте установку при изменении `package-lock.json`. Сборка создаёт `_site`
— готовый сайт для статического хостинга. Просмотр открывается по адресу
**http://127.0.0.1:8080/Baknin_Project/**. Остановка — Ctrl+C.
Установка Python и его зависимостей не требуется.

Эквивалентная прямая команда сборки после `npm ci`:

```bash
node scripts/build_website.mjs --output _site --base-path /Baknin_Project/
```

Для другого репозитория замените базовый путь на его имя. В автоматической
публикации процесс берёт имя репозитория и формирует путь `/<имя>/`.
Для отдельного домена или репозитория вида `username.github.io` измените аргумент
`--base-path` в шаге **Build public website** файла `.github/workflows/pages.yml`
на `/`. Открывайте сайт через HTTP-сервер
просмотра: двойной щелчок по `index.html` не заменяет его, поскольку страницы
загружают данные отдельными запросами.

## Когда нужен отдельный Python-хостинг

На Pages нельзя запустить `app.py`, записывать в SQLite на сервере,
обучать модель или обслуживать Python `/predict`. Если понадобятся эти
возможности в интернете, требуется отдельный Python-хостинг с сохранением
локальных данных между перезапусками. Исследовательский запуск и обучение
описаны отдельно в [LOCAL_TOOLS.md](LOCAL_TOOLS.md).
